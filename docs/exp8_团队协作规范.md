## 2. 协作流程

采用「**需求 → 设计 → 编码 → 测试 → 交付**」瀑布式小迭代流程：

1. **需求阶段**：共同完成调研问卷、访谈与需求规格说明书；
2. **设计阶段**：张三主导 MVC 分层与数据库设计，输出概要/详细设计；
3. **编码阶段**：按模块分工并行开发，接口以文档约定为准；
4. **测试阶段**：王五编写单元测试，张三集成测试；
5. **交付阶段**：李四打包 exe，全组复查文档与提交历史。

## 3. Git 使用规范

### 3.1 分支策略

- `main` 主分支：仅存稳定可发布代码；
- `feature/*` 功能分支：每个功能模块一条，开发完成后合并回 main。

### 3.2 提交信息规范（Conventional Commits）

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| `feat` | 新功能 | `feat: 新增预约提交与冲突检测` |
| `fix` | 缺陷修复 | `fix: 修复取消预约未触发候补转正` |
| `docs` | 文档 | `docs: 新增需求规格说明书` |
| `test` | 测试 | `test: 补充预约模块单元测试` |
| `refactor` | 重构 | `refactor: 备份工具支持注入路径` |
| `chore` | 杂项 | `chore: 新增 .gitignore` |

### 3.3 提交粒度

- 一次提交只做一件事，保持可回溯；
- 提交前本地运行 `python -m unittest discover -s test` 确保不回归；
- 合并前进行代码评审（组长审核心模块）。

## 4. 代码评审要点

1. View 层是否直接访问数据库（禁止）；
2. 业务方法是否返回统一 `(bool, str)`；
3. 密码是否明文（禁止）；
4. 关键操作是否记录 sys_log；
5. 新增代码是否覆盖单元测试。

## 5. 沟通机制

- 每日同步进度与阻塞问题；
- 接口变更须在群内同步并更新概要设计文档；
- 文档与代码同步维护，避免「文档-代码两张皮」。
